## Newly confirmed findings

### V1-A01 — Initiative Roll reference is missing

**Project domains:** Data processing, Web backend, Web frontend

English and Spanish N5.3 p. 15 describe the Lieutenant Attribute roll, repeat
conditions, open Attribute information, and the separation between choosing turn
order and choosing deployment. The archived `Initiative_and_Deployment` page
(revision 3955) corroborates this source area.

The current maintained Core/Hacking records mention Initiative only in
`rule:deployment-phase`, which assumes it has already been resolved. That record's
p. 15 citation does not cover the other procedure on the same page. The published
search API and normal Chromium search return no Initiative result at 1440/390 px.

**Close when:** source-reviewed facts and citations explain the roll and both
choices, are discoverable in normal mode, and are correctly linked from Deployment
and the relevant Lieutenant/Attribute context. No match-state evaluator is required.

### V1-A02 — Combat Group baseline is missing

**Project domains:** Data processing, Web backend, Web frontend

English and Spanish N5.3 p. 10 and archived `Combat_Group` revision 3847 establish
the ten-member group limit, initial assignment, ordinary separation of groups and
the Peripheral counting boundary. Current Regular/Irregular Order, Peripheral,
Fireteam and Strategos explanations use Combat Groups, but do not provide the
baseline capacity explanation. No Core/Hacking maintained summary/fact names the
ten-member limit; published search returns no Combat Group entry at either tested
width.

**Close when:** a linked reference explains the baseline and relevant exceptions,
without conflating group capacity with Army-wide limits or introducing roster
construction/legality validation. Audit the source's separate group-information
and deployed-item ownership clauses in the same bounded slice.

### V1-A03 — Army Retreat and Standard Game context are missing

**Project domains:** Data processing, Web backend, Web frontend

English N5.3 p. 146 and Spanish p. 150 distinguish army-level Retreat from the
Trooper's State. They establish the Tactical Phase survivor calculation, treatment
of undeployed survivors, threshold, Loss of Lieutenant interaction, replacement
Lieutenant restriction, skipped Impetuous Phase, recovery and scenario overrides.
Archived `Retreat!_situation` revision 3942 corroborates the army context.

The published `state:retreat` describes Trooper declarations/cancellation. It does
not represent the army trigger or these army-level consequences. The maintained
Core/Hacking summaries/facts contain no Retreat threshold. Search finds only the
State. `rule:loss-of-lieutenant` also describes appointing a replacement without
linking the army Retreat exception. The Standard Game's duration, Victory Point
comparison and Retreat ending condition likewise need an explicit reference
disposition; four scenario records do not establish coverage of that separate mode.

**Close when:** army Retreat and Standard Game facts are source-reviewed and
usable, the State and Loss of Lieutenant references expose the relevant boundaries,
and scenario-specific end conditions remain authoritative. Avoid a live survivor
calculator or blanket application of Standard Game endings to scenarios.

### V1-A04 — General setup tables stop at audit manifests

**Project domains:** Data processing, Web backend, Web frontend

The direct PDF checks pass for six Game Modes rows on p. 6 and the independently
reviewed Retreat/table guidance on pp. 146–147. The maintained rows include Army
Points, base SWC, table/deployment-zone dimensions, recommended duration and Retreat
thresholds. They remain in `config/validation/game-mode-source-table.json` and
`standard-game-reference-tables.json`, with no normal general-reference publication.
Normal Game Modes search is empty. Scenario-owned dimensions do not publish all
of these facts in their general scope.

The existing backlog's conditional presentation decision is now a concrete v1.0
gap under the requirement to expose useful supported structured information.
Advisory status must remain explicit; it does not make the information unusable to
players. Illustrative terrain names require their own scope decision and are not
eighteen missing canonical Terrain Types.

**Close when:** one maintained general-reference owner publishes the reviewed rows
with normal navigation and citations, distinguishes recommendations from scenario
overrides, and keeps army/session thresholds out of static Unit attributes.

### V1-A05 — Weapon gap triage aborts on completed definitions

**Project domain:** Project infrastructure

The documented enrichment → Weapon Chart → Weapon-definition triage sequence fails
on this baseline with `Reviewed Weapon is not an unresolved identity: Crazykoala`.
Both Crazykoala and Madtraps now have definitions, but the 64-entry shared-effects
policy retains their earlier approvals. `load_shared_reviews()` requires every
review to be a currently unresolved definition. Its test fabricates that condition
for all policy entries, so it misses this real-input integration failure.

An explicitly isolated audit join verified all 64 original profile fingerprints,
confirmed that these two names have no enrichment gaps, and used a separate local
62-review subset. Its output classifies all 63 Weapon audit entries as **62 reviewed
shared-effect omissions plus Flash Pulse's one accepted historical citation**.
This workaround does not repair or pass the documented CLI, certify all Weaponry
clauses, or change the maintained policy.

**Close when:** the CLI handles approved entries that later acquire a definition,
keeps exact source/profile validation, and has a regression using current enrichment
output. Preserve review provenance; do not invent 62 missing definitions or discard
approvals just to make the command run.
