## Newly confirmed findings

### V1-A01 — Initiative Roll reference is missing

**Project domains:** Data processing, Web backend, Web frontend

English and Spanish N5.3 p. 15 describe the Lieutenant Attribute roll, repeat
conditions, open Attribute information, and the separation between choosing turn
order and choosing deployment. The archived `Initiative_and_Deployment` page
(revision 3955) corroborates this source area.

The current maintained Core/Hacking records mention Initiative only in
`rule:deployment-phase`, which assumes it has already been resolved. That record's
p. 15 citation does not cover the other procedure on the same page. The published
search API and normal Chromium search return no Initiative result at 1440/390 px.

**Close when:** source-reviewed facts and citations explain the roll and both
choices, are discoverable in normal mode, and are correctly linked from Deployment
and the relevant Lieutenant/Attribute context. No match-state evaluator is required.

### V1-A02 — Combat Group baseline is missing

**Project domains:** Data processing, Web backend, Web frontend

English and Spanish N5.3 p. 10 and archived `Combat_Group` revision 3847 establish
the ten-member group limit, initial assignment, ordinary separation of groups and
the Peripheral counting boundary. Current Regular/Irregular Order, Peripheral,
Fireteam and Strategos explanations use Combat Groups, but do not provide the
baseline capacity explanation. No Core/Hacking maintained summary/fact names the
ten-member limit; published search returns no Combat Group entry at either tested
width.

**Close when:** a linked reference explains the baseline and relevant exceptions,
without conflating group capacity with Army-wide limits or introducing roster
construction/legality validation. Audit the source's separate group-information
and deployed-item ownership clauses in the same bounded slice.

### V1-A03 — Army Retreat and Standard Game context are missing

**Project domains:** Data processing, Web backend, Web frontend

English N5.3 p. 146 and Spanish p. 150 distinguish army-level Retreat from the
Trooper's State. They establish the Tactical Phase survivor calculation, treatment
of undeployed survivors, threshold, Loss of Lieutenant interaction, replacement
Lieutenant restriction, skipped Impetuous Phase, recovery and scenario overrides.
Archived `Retreat!_situation` revision 3942 corroborates the army context.

The published `state:retreat` describes Trooper declarations/cancellation. It does
not represent the army trigger or these army-level consequences. The maintained
Core/Hacking summaries/facts contain no Retreat threshold. Search finds only the
State. `rule:loss-of-lieutenant` also describes appointing a replacement without
linking the army Retreat exception. The Standard Game's duration, Victory Point
comparison and Retreat ending condition likewise need an explicit reference
disposition; four scenario records do not establish coverage of that separate mode.

**Close when:** army Retreat and Standard Game facts are source-reviewed and
usable, the State and Loss of Lieutenant references expose the relevant boundaries,
and scenario-specific end conditions remain authoritative. Avoid a live survivor
calculator or blanket application of Standard Game endings to scenarios.

### V1-A04 — General setup tables stop at audit manifests

**Project domains:** Data processing, Web backend, Web frontend

The direct PDF checks pass for six Game Modes rows on p. 6 and the independently
reviewed Retreat/table guidance on pp. 146–147. The maintained rows include Army
Points, base SWC, table/deployment-zone dimensions, recommended duration and Retreat
thresholds. They remain in `config/validation/game-mode-source-table.json` and
`standard-game-reference-tables.json`, with no normal general-reference publication.
Normal Game Modes search is empty. Scenario-owned dimensions do not publish all
of these facts in their general scope.

The existing backlog's conditional presentation decision is now a concrete v1.0
gap under the requirement to expose useful supported structured information.
Advisory status must remain explicit; it does not make the information unusable to
players. Illustrative terrain names require their own scope decision and are not
eighteen missing canonical Terrain Types.

**Close when:** one maintained general-reference owner publishes the reviewed rows
with normal navigation and citations, distinguishes recommendations from scenario
overrides, and keeps army/session thresholds out of static Unit attributes.

### V1-A05 — Weapon gap triage aborts on completed definitions

**Project domain:** Project infrastructure

The documented enrichment → Weapon Chart → Weapon-definition triage sequence fails
on this baseline with `Reviewed Weapon is not an unresolved identity: Crazykoala`.
Both Crazykoala and Madtraps now have definitions, but the 64-entry shared-effects
policy retains their earlier approvals. `load_shared_reviews()` requires every
review to be a currently unresolved definition. Its test fabricates that condition
for all policy entries, so it misses this real-input integration failure.

An explicitly isolated audit join verified all 64 original profile fingerprints,
confirmed that these two names have no enrichment gaps, and used a separate local
62-review subset. Its output classifies all 63 Weapon audit entries as **62 reviewed
shared-effect omissions plus Flash Pulse's one accepted historical citation**.
This workaround does not repair or pass the documented CLI, certify all Weaponry
clauses, or change the maintained policy.

**Close when:** the CLI handles approved entries that later acquire a definition,
keeps exact source/profile validation, and has a regression using current enrichment
output. Preserve review provenance; do not invent 62 missing definitions or discard
approvals just to make the command run.

### V1-A06 — The enrichment regression has a stale supporting set

**Project domain:** Data processing

`test_enrichment_coverage_reports_review_mapping_and_source_freshness` fails at

**Close when:** reconcile the two source-owned relationships and update the count
and exact set together. Preserve the assertions for unresolved links and their
classifications; do not weaken totals or drop the new State links to obtain green.

## Existing blockers and acceptance gaps sharpened by this pass

### V1-A07 — Passing catalog audits do not certify the 1.0 scope

**Project domains:** Data processing, Project infrastructure

The enrichment policy still defers missing Weapon definitions and Commlink from
0.10 to v1.0; its zero `releaseBlockerCount` is not a v1.0 verdict. The shared-effect
join above also shows why reclassifying every missing standalone definition as a
blocker would be wrong.

The default interaction command passes a historical **0.7.0 primary scope** and
its current supporting set. The explicit v1.0 candidate reports **184/185 primary
identities complete**, with Commlink pending, and **197 supporting identities**.
The default report's **200 supporting identities** has a different denominator;
neither number establishes whole-source completeness. The strict candidate command
fails on Commlink as intended.

**Close when:** reconcile enrichment/shared-effect dispositions for v1.0, resolve
the Commlink applicability boundary, and activate the appropriate primary gate
without rewriting historical review dates or suppressing unresolved facts.

### V1-A08 — The frozen inventory does not cover the current record set

**Project domains:** Data processing, Project infrastructure

The original explanation inventory remains valid frozen evidence: 367 identities,
304 selected clause reviews and 63 screening-only entries. Current Core plus Hacking
contains **443 records** (431 + 12): **93 additions and 17 removals** relative to
that inventory. The removals are declaration-category identities; additions include
20 declaration identities, 53 Weapon records, 12 Rules, five terms, two Skills and
one Equipment record. Identity change is not evidence of a defect or absent review.

The fresh reference baseline inventories 23 published categories and 122 source
groups, but deliberately leaves final fact/relationship/presentation dispositions
pending. The 303 source PDF bookmarks screened here are discovery entries, not
303 semantic approvals. V1-A01 demonstrates why a same-page citation cannot certify
a different clause or source heading.

**Close when:** retain the frozen evidence and join it to the current identities,
renames, later source reviews and browser evidence. Give each current in-scope
category/section a reviewed disposition and turn concrete omissions into bounded
work. Do not reset historical counts or treat every added record as unreviewed.

### V1-A09 — Occurrence parameters and the usage index remain open

**Project domains:** Data processing, Web backend, Web frontend

The raw/application/rules-pair auditor reproduces **37 Skill and 14 Equipment source
IDs** with unresolved occurrence parameters. These are source IDs, not 51 bugs or
51 missing definitions. High-occurrence examples include BS Attack, Immunity,
Terrain, Hacker, Hacking Device, MediKit, GizmoKit and Deactivator. Existing typed
Mimetism/Berserk/Dodge/Surprise Attack mappings do not close these other meanings.

The cross-army usage index remains explicitly unimplemented in the data model.
Review exact source signatures by semantic family before index materialization;
preserve raw labels and ambiguous combinations. Required facts and context must be
usable, but optional comparison/search controls are not an independent release gate.

### V1-A10 — Reinforcements procedural authority is unresolved

**Project domain:** Data processing

The source-applicability audit verifies two current N5/ITS references and two
historical N4 annex PDFs while reporting `n5ProceduresAuthorized: false`.
Commlink remains exposed with no reviewed definition. A reference to an unversioned
annex does not establish that the available N4 procedures apply unchanged to N5.

Identify and pin an official N5-applicable revision/adoption ruling, or explicitly
resolve the supported reference boundary under the existing release policy. If
procedures are supported, deliver their typed parameter, phase and browser slice.
This is an unresolved authority/disclosure decision, not a claim that no such
official evidence exists elsewhere or that a publisher must issue a new ruling.

strict-primary failure on Commlink. Passing output includes:

- exact Army archive/list provenance and selected nested occurrence parity;
- all 113 requested archived Wiki revisions and the supplied snapshot/PDF pins;
- zero occupied fields among the 39 statically unrepresented Army candidates;

- bounded delivery coverage for all 17 published objects, reviewed lexical queues,
  Restrictions, Orders/AROs, Hacking, Silhouette and other selected source tables;
- matched deployed-object publication and all 808 published assets.

The selected normal browser discovery checks passed eight pages at 1440/390 px,
with no page errors, failed/HTTP-error requests or horizontal overflow. They confirm
the search omissions above, not whole-application browser acceptance.

The broader targeted test run reported **413 passed, 16 skipped, one failed**;
V1-A06 names and reproduces that failure. The separate opt-in tracked-pair FAQ
browser run passed **16 tests**. Full final-candidate, whole-documentation, hosted CI,
manual Silhouette interaction, deployed verification and host rollback/forward
acceptance remain governed by the existing release checklist. This audit does not
substitute for those gates.

Accurately disclosed publisher disagreements remain non-blocking under the release
policy. The Kobra/Weapon Trait/Mine/Dazer source differences must not be silently
converted into application corrections. Final source disclosure acceptance remains
necessary even when an external correction is deferred.
