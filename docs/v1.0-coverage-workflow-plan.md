# V1S-082 source-coverage workflow optimization plan

**Project domains:** Data processing, Web frontend, Project infrastructure  
**Status:** accepted optimization direction; implementation phased, not a source-coverage sign-off.  
**Owner:** [V1S-082](TODO.md#final-frozen-candidate-acceptance-and-release) with final acceptance in [releasing](releasing.md#version-10-data-completeness-gate).

## Problem and boundaries

The 2026-11-06 live `tools.report_reference_baseline --reconcile-explanation-inventory` inventory contains **466 current Core/Hacking identities** and **830 distinct cited source locators**. A locator is a source/page/heading discovery key, not an independently approved clause, defect, or unit of labor. The historical 367-record comparison remains frozen evidence, and later bounded reviews are not whole-record approvals.

V1S-082 requires both directions of coverage:

1. **Record to source:** every material maintained claim has correct versioned provenance, conditions, exceptions and uncertainty.
2. **Source to record to ordinary browser:** every in-scope source concept, including concepts with *no existing record*, has a maintained owner and usable normal-browser presentation, or a reasoned, documented exclusion/disclosure.

Do not equate citation presence, source-hash parity, route existence, reviewed curated status, a prior targeted test, or shared wording with semantic approval. Avoid speculative new gameplay rules, universal cross-record inference, roster/construction engines and optional post-1.0 ITS content. The [release definition](releasing.md#version-10-data-completeness-gate) governs exclusions.

## Optimization strategy

- **Reuse one baseline.** Extend `tools.report_reference_baseline` and existing source/semantic/route audits. Generate reproducible, deterministic batches from its current identity and locator inventory; never create another independent source ledger by hand.
- **Separate mechanical and semantic evidence.** Machine checks can prove identity/provenance/parity/link and selected route outcomes. A reviewer must independently adjudicate rule meaning and source-wide omissions. Make the status `pending` unless accepted with explicit evidence.
- **Cluster related work.** Group by material semantic family and shared source locations. Inspect each versioned clause and its exceptions once per source fingerprint, then apply that reviewed finding to explicitly listed record owners. A page-level match is only a triage hint.
- **Persist signed-off dispositions.** Introduce a small, versioned, tracked review manifest once the planner has been exercised. Use stable record/source-clause keys; disposition values should distinguish accepted, accepted-with-disclosure, excluded-with-rationale, blocked/source-conflict and confirmed-defect. Record reviewer, exact source/version/section and relevant API/browser evidence. Do not silently migrate approvals after a source change.
- **Incremental invalidation.** Fingerprint relevant source files/revisions and curated facts, plus API/browser contract when claimed. A changed fingerprint makes dependent evidence stale (not deleted or auto-approved); unaffected findings remain reusable. Cross-reference proof dependencies explicitly.
- **Automate source-first discovery.** Compare PDF sections, archived Wiki/FAQ/Army source inventories, declarations, special objects and supported scenario concepts with curated owners. Report uncovered source concepts separately from record-centric proof gaps. Translation and diagram-only semantics require a scoped manual review.
- **Validate intelligently.** Reuse template-level route/accessibility checks for ordinary pages and run exception-specific browser cases only where behavior differs. Use the canonical 3-VD/5-VR phased queue and pinned Linux test protocol. Never count an unexecuted or skipped test as passed.

## Implementation slices and acceptance

### P0 — read-only work planner (first implementation slice)

Extend the existing explanation-inventory reporter with an opt-in, JSON-only batch planner. It must:

- Consume its exact current `currentRecords`, `sourceSections` and fingerprint data rather than reparse the PDF corpus or reconstruct a second identity list.
- Create stable, bounded source-family work groups including full record IDs and original source locator keys, while listing cross-owner shared locators separately for reuse.
- Show current/frozen inventory counts, total unique locators, record-locator occurrences, historical S records, post-inventory additions, selected browser-test pointers and source-variant candidates **as triage information only**.
- Mark every record and locator *pending* until a separate reviewed disposition exists; never subtract historical bounded evidence from the accepted denominator.
- Fail on missing/duplicate IDs or missing source-key mappings; keep output deterministic and confined to an explicitly requested path (normally `local/`).
- Receive static test designs through VD and deferred execution through VR; structural lint/type/docs and read-only CLI output may run immediately.

**Implemented 2026-11-06:** `tools.report_reference_baseline --reconcile-explanation-inventory --review-batches-output local/audits/v1s082-review-batches.json` produces the ignored, deterministic JSON triage index. The first actual run grouped **466 records into 18 batches**, cross-referenced **828 source locators** (including **92 shared locators**) and issued **zero approvals**. A later Windows run executed the VR-0119/0120 planner/pilot selectors and baseline regressions: **110 passed, 5 optional skips, zero failures**; required selectors had no skips. The pilot work packet preserves explicit archived-Wiki `member` values, reports known and unresolved source-page identities separately, and suppresses page totals/reuse figures if any identity is incomplete. The current page-identity regressions remain deferred under **VR-0123**. This is a usable inventory optimization, not the P1 disposition system.

### P1 — tracked disposition and source-evidence contract

Introduce a minimal schema under `config/validation/` with exact typed owners, source fingerprint, clause/exception keys, reviewed scope and supporting test selectors/results (including commit and target host). Validate duplicates, stale keys, malformed status, evidence drift and orphaned source-first concepts. Start with a representative **30–40 record pilot**; do not backfill inferred approvals.

**Initial safety contract (2026-11-06):** The maintained, read-only `tools.source_coverage_dispositions` validator consumes `config/validation/source-coverage-dispositions-v1.json`, existing current Core/Hacking identities, exact curated-record JSON hashes, and already declared source SHA-256 pins. A review is uniquely keyed by source identity, printed page/archive member and stable clause key; it has explicit record owners, semantic scope, source-first or record-first origin, dependencies, separate semantic/browser dispositions, and, when accepted, reviewer/date/evidence. Browser acceptance additionally needs exact application Git SHA, matched database hashes, test selectors and file-level contract fingerprints. Missing owners, source pins, required acceptance evidence, stale fingerprints, duplicate clauses, unsupported statuses and dependency cycles fail closed. The validator does **not** read source PDFs, decide rule correctness, discover unowned clauses, infer a complete page/record, run tests, or award source-wide acceptance. It was introduced with **zero** review entries and zero approvals; the first [four language-specific, clause-scoped dispositions](v1.0-source-coverage-audit.md#v1s-082-p1-source-clause-evidence-deployable-and-target-attribute-2026-11-06) now cover two Trait identities without accepting browser or whole-record scope. Continue migrating only independently reviewed claims, never historical flags or the 40 scoped benchmark triage decisions automatically. The testing guide owns its invocation.

**Corrected locator-count observation (not a measured review benchmark):** the 129 citation occurrences map to 125 exact source/page/heading locators (4 duplicate locator occurrences) and 97 `(sourceId, page)` buckets. The 97 buckets are **not distinct pages**: nine page-less Wiki locators carry explicit curated archive `member` values, resolving the 35-record pilot to **104 source-page identities** and **25 citation-occurrence page-reuse candidates**. These are identity-based counts, not actual opens or saved reads; when a member is absent or ambiguous, the planner reports unresolved identity and suppresses total-page and reuse figures. Including the three source-first probes, the existing PDF-only mechanical replay's **102 record-first / 79 family-batched page references**, plus **30 Wiki citation occurrences / 27 exact Wiki identities**, gives a citation-occurrence ceiling of **132 references / 106 identities**: at most **26/132 (19.7%)** fewer requests if every citation caused a separate page access. This is not observed source-opening or review effort; a record-first reviewer may already reuse pages within a record. The replay did not reopen the Wiki sources, and the completed screening did not capture elapsed review time or actual source-open events, so neither can be reconstructed from locator counts.

**Measured mixed-screen benchmark (2026-11-06):** a separate risk-stratified
40-record run covered ten kinds, with 20 different records per arm. The
record-first arm logged **20 PDF page-access events** and **93.65 s** wall
time; the family-batched arm logged **18 events** and **89.61 s**. It recorded
40 separate per-record triage decisions, not 40 approved source clauses:
34 scoped claims were supported and six remained unresolved. Four ordinary
browser routes and two known source controls were checked separately. Fixed
arm order, different records, cropped pages, one reviewer and a one-claim scope
make these exploratory observations, not an estimate of full-review savings or
active reviewer time. See the [benchmark evidence](v1.0-source-coverage-audit.md#v1s-082-mixed-screen-benchmark-2026-11-06).

### P2 — source-first negative coverage

Independently enumerate versioned PDF contents/section exceptions, the scoped Army/Wiki/FAQ identities, and known deliberate omissions. Join to current owners. Flag source concepts without a published home, and keep exclusions and disputed sources explicit. Record uncertainty rather than inventing mappings.

### P3 — incremental checks and batch acceptance

Implement changed-input invalidation and family-scoped API/route checks; reuse already accepted source-clause evidence only with matching fingerprints and exact scope. Provide deterministic progress output: pending, accepted, accepted-with-disclosure, excluded, blocked and confirmed-defect counts plus staleness. Source-cited and browser acceptance remain distinct dimensions.

### P4 — final V1S-082 reconciliation

Review all material source-first omissions, every in-scope record/condition and the remaining unaccepted browser paths; reconcile confirmed fixes, source conflicts and the canonical VD/VR queue. Preserve V1S-083–095 frozen-candidate/release/host acceptance as *separate* gates.

## Benchmark and stop conditions

Use a representative 30–40 record pilot, deliberately mixing straightforward metadata, a shared-citation family, complex conditional Hacking/combat, a bilingual conflict and a missing-source-concept case. Compare to the current per-record workflow: reviewer/agent time, redundant source opens, unique semantic decisions, defects found, false positive/negative triage, evidence reuse and browser validation coverage. Initial optimization target: **at least 50% less repeated review effort**, not an asserted achieved saving. Re-estimate work only from measured pilot results.

Before using a benchmark to decide that target, define equivalent completed
record/source/browser scope in both arms, include the omitted source types and
domains in the sampling frame, and measure active repeated-clause review
separately from unique work and idle/tool time. Counterbalance order or use
independent reviewers, record actual source accesses and interruptions, and
assess quality against independent, blinded omission and conflict controls.
Compare repeated active effort only for equal completed scope without a loss
of quality; report total effort and uncertainty separately. The mixed-screen
run above does not satisfy this gate.
